# Editor mouse lockout — 2026-09-03

## Evidence

The saved heap dump had an unfocused/unhovered GamePreviewer with its camera updates disabled but `m_bIsManipulatingView = true`. ImGui had `NoMouse` set, cursor `None`, and all mouse buttons released. The excavation trace continued producing completed ticks; keyboard strikes still changed the specimen. No active ImGui window drag was present in the dump.

`EditorTool::PostDrawUpdate` kept suppressing UI mouse input based on the stale manipulation flag. A disabled camera returned before clearing that flag and could not observe release. The initial focus-loss event itself was not captured.

## Repair

- `ToolsCameraComponent::SetUpdateEnabled(false)` clears manipulation immediately.
- `Update` resets manipulation before its disabled early return.
- EditorTool requires visibility, focus, an actually held camera mouse button, and no Escape/app-focus cancellation before requesting mouse suppression.
- EditorUI clears the global mouse suppression bit once at FrameStart, before early returns/tool destruction. Eligible tools only add requests, so inactive tools cannot revoke a focused tool's request. The preview can add its request at FrameEnd.
- No granite geometry, excavation, accounting, input bindings, or collision changes.

## Verification

Debug editor and engine dependencies built successfully. An isolated C++ harness generated by `editor_mouse_regression_source.py` uses the production setter and PostDrawUpdate bodies, plus the disabled Update entry path, with stubbed input/UI services. It passed 784 checks in /Od and /O2 builds. It covers all 256 visibility/focus/hover/manipulation/button/Escape/app-focus combinations, the saved lockout state, release/reacquisition, multiple-tool ordering, and closing the last tool.

This is state-transition coverage, not automated Windows UI/focus testing. The source generator emits C++ to stdout; the generated harness and run script are in Build/x64_Debug. Regenerate the harness when production methods change.
